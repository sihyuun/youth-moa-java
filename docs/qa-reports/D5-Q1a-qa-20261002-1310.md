### 1-1. ProgramStatusDerivationTest 테스트 코드 품질 검토

- case 1 (UPCOMING): `applyStart=today+3, applyEnd=today+10, startDate=today-10, endDate=today+30` — 운영기간이 과거 시작이어도 UPCOMING 판정. **Q5=A 와 반대 축인 UPCOMING 측 보증 OK**.
- case 2 (OPEN): `applyStart=today-2, applyEnd=today+5` + D-day=5 검증. 1-step 검증 (status + D-day 동시 체크) 로 효율적.
- case 3 (ENDED, 핵심): `startDate=today+10, endDate=today+60` 미래 운영기간 + `applyEnd=today-1` → ENDED. **Q5=A ("운영기간 무관") 를 가장 정확히 포착**.
- case 4 (경계 D-DAY): `applyEnd=today` → OPEN + D-DAY. **off-by-one 재발 방지** 가치 큼.
- case 5 (SUSPENDED 최우선): isActive=false 조합, applyPeriod OPEN 범위에서도 SUSPENDED 판정.
- case 6 (nullable 폴백): 3가지 서브케이스 (UPCOMING/OPEN/ENDED) 모두 커버. **적절**.

**지적**: 폴백 case 에서 `applyEnd=null, endDate=today-5` 조건에 Q5=A 에 상응하는 "endDate 는 미래지만 applyEnd 가 null 이고 startDate 는 과거" 같은 복합 폴백 미검증. 다만 D5-Q1d 머지로 폴백 자체가 제거될 예정이라 추가 case 는 불필요.

### 2-2. 뱃지 분포 실측 (중대한 발견)

`/programs` 목록 응답에서 D-day 뱃지 분포:

```
종료 2건 · D-6 · D-8 · D-9 · D-12 · D-13 · D-15 · D-20 · D-34 · D-45 (각 1건)
```

D-day 숫자가 ym-impl 가 DataInitializer 에 세팅한 **applyEndDate 역산 시드와 일치** (예: `D-6` ↔ `applyEndDate(today.plusDays(5))`). 즉 **ProgramCardDto 가 Program.getStatus() + getDdayLabel() 호출 경로를 통해 신청기간 기준으로 뱃지가 이미 변경되었음**.

상태 라벨은 OPEN 2건("모집중"), UPCOMING 6건("예정") 노출 — 페이지네이션 기본 10건 한계로 전체 24건 분포는 불가.

### 2-3. 💥 ym-impl 보고 상충 지적 (중요)

ym-impl 보고 "consumer 미교체 상태라 뱃지 변화는 없어야 함" + 디자인 계약 L84~89 "소비 지점은 **아직 운영기간 기준**" 전제가 **실제 코드와 불일치**합니다.

**결론**: D5-Q1a 머지는 "엔티티 메서드만 교체" 가 아니라 **ProgramCardDto·ApplicationService·AdminDashboardService·AdminStatsService·CSV·캘린더 뱃지의 동작까지 암묵적으로 교체**합니다.

이게 **의도된 설계**라면 (사실 자연스러운 결과) OK. 다만:
- 디자인 계약 문서(`docs/design-contracts/program-status-derivation.md` §7) 가 "D5-Q1b 로 이월" 로 적어 둔 지점 중 **ProgramCardDto / AdminDashboardService / AdminStatsService / ProgramCalendarService 는 이미 Q1a 머지로 교체 완료**됨. 문서를 사실에 맞춰 정정 필요.
- 여전히 운영기간 기준인 지점: **ProgramSpec (status DB 필터)** — `ProgramSpec.java:56-64` 가 `startDate/endDate` 를 기준으로 쿼리. 사용자가 `?status=upcoming` 필터 하면 DB 는 운영기간 기준 10건 반환, 그 10건의 뱃지는 신청기간 기준 섞인 상태 (OPEN/UPCOMING/ENDED 혼재) 로 보임. **이게 Q1b 로 이월된 "진짜 상충"**.

### 2-4. ProgramSpec 상충 재현 가능성

```java
// ProgramSpec.java:61
case "upcoming" -> (root, query, cb) -> cb.greaterThan(root.get("startDate"), today);
```

시드 데이터 중 "D5-Q1a: UPCOMING" 의도 (applyStart 미래, startDate 미래) 는 겹치므로 당장은 눈에 안 띔. 하지만 "applyStart 미래 + startDate 과거" (운영은 이미 시작했지만 신청만 늦게 열림) 조합이 들어오면 뱃지 UPCOMING ↔ DB 필터 미매칭 발생. 운영 데이터에서는 발생 가능성 있음.

- 폴백 테스트 case 6 이 유일한 안전망.

**결론**: 폴백 리스크 낮음. backfill 이월 결정은 적절.
